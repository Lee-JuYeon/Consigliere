# Coding Model Strategy — Opus 완전 대체 프로젝트

> 작성일: 2026-03-30
> 관련 프로젝트: CLI Company, Beethovain, Ledger, ProjectModel
> 목표: 8GB 메모리 환경에서 Claude Opus를 완전 대체하는 코딩 특화 블렌딩 모델 개발

---

## 1. 배경

### 문제
- CLI Company는 현재 Claude Opus/Sonnet에 의존
- 무과금("쌀먹") 유저의 대안은 DeepSeek, Qwen 등 **중국제 모델뿐**
- 코딩 작업은 API 키, .env, DB 크레덴셜 등 **민감 정보를 입력** → 중국 모델 = 보안 리스크

### 목표
- 비중국 오픈소스 모델 블렌딩으로 **코딩 특화 모델 개발**
- **8GB 메모리**에서 구동 가능
- CLI Company 무과금 유저에게 **안전한 코딩 AI** 제공
- Opus **완전 대체** (단계적이 아닌 절대적 대체)

## 3. Opus 대체를 위한 3대 과제

### 과제 1: 추론 깊이 (가장 큰 병목)
**문제**: 7B 모델은 1~2단계 추론은 잘하지만, Opus처럼 5~6단계 연쇄 추론이 약함.

**해결 전략:**
| 방법 | 설명 | 담당 |
|------|------|------|
| Test-Time Compute | 작은 모델이 오래 생각하게 함 (chain-of-thought 확장) | ProjectModel |
| MoE (Mixture of Experts) | 내부 전문가 분리로 실질 추론력 향상 | ProjectModel |
| Distillation | Opus 결과물을 Teacher로 소형 모델 학습 (법적 확인 필요) | Beethovain |
| 코딩 특화 LoRA | 범용성 버리고 코딩에만 올인한 파인튜닝 | ProjectModel |

### 과제 2: 컨텍스트 윈도우 → Ledger로 해결
**문제**: Opus 200K 토큰 vs 7B 8K~32K 토큰.

**해결: Ledger 통합 구조 (뇌 모델)**

```
┌─────────────────────────────────────────────┐
│              Ledger                   │
│                                              │
│  ┌──────────────┐    ┌──────────────┐       │
│  │ DocumentPipe │    │   CodePipe   │       │
│  │ (우뇌)       │    │   (좌뇌)     │       │
│  │              │    │              │       │
│  │ goldmark     │    │ tree-sitter  │       │
│  │ MD 파서      │    │ AST 파서     │       │
│  │ 헤딩 청킹    │    │ 심볼 청킹    │       │
│  └──────┬───────┘    └──────┬───────┘       │
│         │                   │                │
│         ▼                   ▼                │
│  ┌──────────────────────────────────┐       │
│  │     Unified Store (SQLite)       │       │
│  │     뇌량 (Corpus Callosum)       │       │
│  │                                   │       │
│  │  chunks (type: "doc" | "code")   │       │
│  │  relations (코드↔문서 교차 참조)  │       │
│  │  symbols (심볼 테이블)            │       │
│  │  call_graph (호출 관계)           │       │
│  └──────────────┬───────────────────┘       │
│                 │                             │
│         ┌───────┴───────┐                    │
│         ▼               ▼                    │
│  ┌────────────┐  ┌─────────────┐            │
│  │UnifiedSearch│  │  CrossRef   │            │
│  │코드+문서    │  │ 코드↔문서    │            │
│  │동시 검색    │  │ 자동 연결    │            │
│  └────────────┘  └─────────────┘            │
└─────────────────────────────────────────────┘
```

- **DocumentPipe (우뇌)**: MD 파일 헤딩 기반 청킹, 시맨틱 검색 — 문서/대화 컨텍스트
- **CodePipe (좌뇌)**: tree-sitter AST 기반 청킹, 심볼/호출 그래프 — 코드 컨텍스트
- **Unified Store (뇌량)**: 하나의 SQLite DB에 통합 저장
- **CrossRef**: 코드↔문서 자동 연결 (코드가 어떤 규칙을 구현하는지, 어떤 이슈와 관련되는지)

### 과제 3: 지시 수행 정확도
**해결:**
| 방법 | 설명 | 담당 |
|------|------|------|
| Distillation | Opus의 지시 수행 패턴을 소형 모델에 학습 | Beethovain |
| Instruction Decomposition | 복잡한 지시를 단계별로 분해 → 하나씩 실행 | ProjectModel |
| Self-Verification | 생성 후 스스로 체크리스트 대조 (TTC 활용) | ProjectModel |

## 4. 8GB 메모리 제약

### 현실적 가용 메모리
| PC 스펙 | OS/기본 프로그램 | 모델 가용 메모리 |
|---------|-----------------|-----------------|
| 8GB | ~4-5GB | **~3-4GB** |
| 16GB | ~8GB | **~8GB** |

### 사용 가능 모델 (비중국, 오픈소스, Q4 양자화)
| 모델 | 파라미터 | Q4 크기 | 출처 |
|------|---------|---------|------|
| Phi-4 Mini | 3.8B | ~2.5GB | Microsoft |
| StarCoder2 3B | 3B | ~2GB | BigCode |
| Gemma 2B | 2B | ~1.5GB | Google |
| Granite Code 3B | 3B | ~2GB | IBM |
| Code Llama 7B | 7B | ~4GB | Meta |
| Codestral Mamba 7B | 7B | ~4GB | Mistral |
| StarCoder2 7B | 7B | ~4GB | BigCode |
| Granite Code 8B | 8B | ~4.5GB | IBM |

### 블렌딩 전략 (8GB 제약)
| 전략 | 가능 | 이유 |
|------|------|------|
| Routing | O | 한 번에 하나만 로드 |
| Cascade | O | 순차 실행, 하나씩 로드/언로드 |
| Merging | O | 오프라인에서 합쳐서 단일 모델 생성 |
| Ensemble | **X** | 동시 로드 필요 → 메모리 초과 |

**최적 전략**: Merging + Cascade
```
[코딩 요청]
  ├─ 일반 → Merged 3B 경량 모델 (~2.5GB)
  └─ 복잡 → 3B 언로드 → 7B 모델 로드 (~4GB) Cascade 폴백
```

## 5. 전체 연동 흐름

```
[CLI Company Agent]
  → API 요청
  → [Ledger] 관련 코드/문서 검색 (50ms)
      ├── CodePipe: 관련 함수/타입/의존성
      ├── DocumentPipe: 관련 규칙/이력
      └── CrossRef: 코드↔문서 연결
  → [ProjectModel / 로컬 Ollama]
      → Beethovain 블렌딩 모델 (GGUF)
      → Ledger 컨텍스트 + 유저 요청 → 응답 생성
  → 민감 데이터가 외부로 나가지 않음
```

## 7. 학습 데이터 수집 — 데이터 이코노미 모델

### 핵심 아이디어
유저가 LLM CLI를 통해 생성한 프롬프트+코드를 공유받아 학습 데이터로 활용.
대기업 개발자가 Opus/Sonnet에게 시킨 코드 = 고품질 instruction+output 쌍.

### 데이터 플라이휠
```
유저가 코드 공유 → 학습 데이터 증가 → 모델 품질 향상
       ↑                                    │
       └──── 더 좋은 모델 → 더 많은 유저 ←──┘
```

### 보안 — On-Device 전처리 (필수)
```
[유저 PC]
  ├── 프롬프트 + 코드 생성
  ├── [On-Device Sanitizer] ← 유저 PC에서 실행, 서버 전송 전
  │   ├── API 키, 토큰, 크레덴셜 제거
  │   ├── 내부 URL, IP 주소 제거
  │   ├── 회사명, 프로젝트명 익명화
  │   ├── 비즈니스 로직 → 코드 패턴만 추출 (선택)
  │   └── 유저가 미리보기 후 승인
  └── [승인된 데이터만 전송] → ProjectModel 학습 데이터 풀
```

### 수집 방식 옵션
| 방식 | 안전도 | 데이터 품질 | 설명 |
|------|--------|-----------|------|
| Opt-in + 미리보기 | 높음 | 높음 | 유저가 직접 보고 승인한 것만 전송 |
| 코드 패턴만 추출 | 최상 | 중간 | 변수명/로직 익명화, 구조 패턴만 학습 |
| 공개 프로젝트 한정 | 최상 | 낮음 | GitHub public repo 코드만 수집 |

### 보상 티어 구조
```
┌─────────────────────────────────────────────────────┐
│                                                      │
│  [Free] 기본 유저                                     │
│  ├── 데이터 공유 안 함                                │
│  ├── 일일 사용량 제한                                 │
│  ├── 기본 모델만 사용                                 │
│  └── 자동화 기능 없음                                 │
│                                                      │
│  [Contributor] 공유 유저                              │
│  ├── 코드/프롬프트 데이터 공유 (Sanitized)            │
│  ├── 사용량 무제한                                    │
│  ├── 자동화 기능 (CI/CD 연동, 배치 작업 등)           │
│  ├── 최신 블렌딩 모델 즉시 액세스                      │
│  └── 공유량에 비례한 크레딧 적립                       │
│                                                      │
│  [Veteran] 지속 공유 유저                             │
│  ├── 일정 기간 이상 지속적으로 공유                    │
│  ├── 최고 성능 모델 무료 무제한                        │
│  ├── 베타 모델 얼리 액세스                            │
│  ├── 커뮤니티 뱃지/인정                               │
│  └── 모델 커스터마이징 우선권                          │
│                                                      │
└─────────────────────────────────────────────────────┘
```

### 크레딧 시스템
```
[공유 행동]                         [크레딧]
프롬프트+코드 1건 공유               +1
공유 코드가 학습에 채택됨             +5 (품질 보너스)
연속 30일 공유                       +50 (지속성 보너스)
버그 리포트 포함 공유                 +3
다언어 코드 공유 (Swift+TS 등)       +2

[크레딧 사용]
자동화 기능 이용                     -10/월
최신 모델 액세스                     -20/월
커스텀 LoRA 요청                     -100
```

### 유료화 공존 모델
```
돈으로 살 수도 있고, 데이터로 살 수도 있음

[방법 A] 월 $10 결제              → Contributor 티어
[방법 B] 데이터 공유              → Contributor 티어 (무료)
[방법 C] 둘 다                   → Veteran 티어 빠르게 달성
```

### 부트스트래핑 철학 적합성
- 돈이 아니라 **데이터가 화폐** → 투자 없이 모델 성장
- 유저: "$0으로 좋은 모델 사용"
- 우리: "투자 없이 학습 데이터 확보"
- CLI Company 기존 $0 유저 비용 원칙과 완전 호환

### 법적 리스크 대응
| 리스크 | 대응 |
|--------|------|
| 기업 코드 유출 | Opt-in + 미리보기 승인 필수. 유저 책임 동의 |
| NDA 위반 | 이용약관에 "공유 권한이 있는 코드만" 명시 |
| 저작권 | 오픈소스(MIT) 모델 → 학습 데이터도 오픈 기여 라이선스 |
| GDPR/개인정보 | On-Device 전처리 + 서버에 원본 미저장 |
| 품질 보장 | 채택 심사 (자동 린트/테스트 통과 여부) + 커뮤니티 리뷰 |

## 8. Ledger 구현 현황 (2026-03-31)

### Phase 1 완료 — DocumentPipe + BM25
- Go 단일 바이너리 (7MB), 외부 의존성 0
- `ledger index` → MD 파일 파싱, 헤딩 기반 청킹, SQLite FTS5 인덱싱
- `ledger search "쿼리"` → BM25 검색, 필터(--type, --tag, --after, --before)
- `ledger status` → 인덱스 상태 확인
- CLI Company에서 테스트: 32파일, 137청크 인덱싱 완료
- LLM/Ollama 불필요. 순수 알고리즘 검색

### 메모리 사용량 분석 (최종 Phase 기준)

```
16GB PC 기준:
├── OS + 기본 프로그램:     ~8GB
├── Ledger 자체:           ~20MB  (거의 안 먹음)
├── Ollama + 임베딩:       ~800MB (코딩 모델과 공유)
├── 코딩 모델 3B:          ~2.5GB (일반 코딩)
│   (또는 7B:              ~4GB)  (복잡한 코딩, Cascade)
└── 여유:                  ~4.7GB / ~3.2GB

8GB PC 기준:
├── OS + 기본 프로그램:     ~4.5GB
├── Ledger + Ollama:       ~820MB
├── 코딩 모델 3B:          ~2.5GB (이것만 가능)
└── 여유:                  ~180MB (빡빡)
```

| 구성 요소 | RAM | 디스크 | 비율 |
|-----------|-----|--------|------|
| Ledger 자체 | ~20MB | 7MB | 0.4% |
| Ollama + 임베딩 | ~800MB | ~800MB | 17% |
| **코딩 모델 (3B/7B)** | **~2.5~4GB** | **~2.5~4GB** | **52~83%** |

→ Ledger는 거의 안 먹고, Ollama는 코딩 모델과 공유. 메모리 주범 = 코딩 모델.
